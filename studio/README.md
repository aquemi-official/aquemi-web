# Studio kit

Development and design tooling for a static website, built to be worked by people and Claude agents together. Drop the `studio/` folder into any website project and you get:

- **Page history.** Any page as it was at each named checkpoint or at any commit, flipped or compared side by side, desktop or phone.
- **Media gallery.** Every image made or considered for the site, used or not, tagged by what became of it.
- **Style atlas.** Images taken apart into text-to-image keywords and reusable prompts; the keywords counted; families; what scored with the brand and what failed; the prompt kit new images are made from (image → text → image).
- **Site scans.** Other sites taken apart (sitemap, page outlines, calls to action, the words they use) and set against ours, so sitemap and copy decisions start from what the market does.
- **Motion porting.** The Subframe Motion library (300+ MIT examples), searched and ported into the project's own stack.
- **The studio bar** across the draft site and every tool, with a page jump, open notes, toggles and a link to each page's history.
- **One release step** that leaves all of it out of the live site, and a live preview to review before switching.
- **Claude Code skills** for each workflow, and a workflow script for describing images in parallel.

The kit never names a project. A project describes itself in one file at its root, **`studio.config.json`**: name and brand, where its pages and data live, its branches and published copies, what the live site is made of, and its own extra tools, skills and notes. Python 3.8+ standard library only; Pillow, if installed, adds thumbnails and WebP.

## Set up in a project

```bash
cp -r <path to a kit>/studio ./studio      # the folder, as is
python studio/studio.py init               # writes studio.config.json from what it finds, adds the studio bar to the
                                           # site's pages, installs the skills, builds
python studio/studio.py doctor             # git, Pillow, network, config
python studio/studio.py check              # 0 problems: the live site can be released cleanly
```

Then review `studio.config.json` (brand, `live.keep`, branches), and optionally:

- Copy `studio/templates/github/pages.yml` and `check.yml` into `.github/workflows/` (Pages source: GitHub Actions).
- Copy `studio/templates/mcp.json` to `.mcp.json` for the motion library's MCP server.
- Serve the project root (`python -m http.server 8000`) and open `/studio/web/index.html`, the hub.

Updating the kit later: replace the `studio/` folder, then `python studio/studio.py install` (refreshes the skills in `.claude/skills/` and the studio section of `AGENTS.md`) and `check`.

## How it fits together

```
studio.config.json (project) ─┐
studio/kit.json   (kit tools) ─┼─► studio/web/studio.js     the bar + window.STUDIO      (generated by build)
                               ├─► <data.dir>/studio.json   what the hub shows           (generated by build)
the site's pages ──adapter─────┴─► <data.dir>/pages.json    the kit's view of the site   (generated by build)

python studio/studio.py  about · status · refresh · check · release · assemble · install · init · doctor
                         pages · history · gallery · atlas · prompts · scan · motion
```

| Folder | What |
| --- | --- |
| `studio.py` | The CLI. `python studio/studio.py help` lists every command. |
| `kit.json` | The kit's registry: its tools (hub, history, gallery, atlas, scans) and skills. |
| `lib/` | `config.py` (loads the config with defaults), `pages.py` (page adapters), `core.py` (build, status, refresh, check, release, assemble, install, init, doctor), `history.py`, `gallery.py`, `atlas.py`, `scan.py`. |
| `web/` | The viewers (`index.html` hub, `history.html`, `gallery.html`, `atlas.html`, `scans.html`), `studio.css` (bar, viewer base, token defaults), `src/bar.js` (bar source), `studio.js` (**generated**), `history-sw.js` (copied into the history folder by `build`). |
| `skills/` | Claude Code skills, copied into `.claude/skills/` by `install`: `studio`, `studio-image-loop`, `studio-motion`, `studio-site-scan`. |
| `workflows/` | `describe-images.workflow.js`: image → text for many images at once, then the atlas. |
| `tools/` | `image-loop/` (section prompts, Gemini helpers, capture), `motion/` (Subframe Motion client and catalog), `images/` (WebP, line art to mask, icon sheet cutter; Pillow). |
| `schemas/` | The data contracts: config, pages, gallery, image description. A project's own producer writes the same shape. |
| `templates/` | Starter config, the `AGENTS.md` section, GitHub workflows, `.mcp.json`. |

## The config

Every path is relative to the project root. Only `project.name` is required; the rest has defaults (`lib/config.py`). The fields that matter most:

| Field | What |
| --- | --- |
| `project` | `name`, `about` (what the business is, who reads the site), `repo` (`owner/name`), `url` |
| `brand` | `book` (brand book file), `summary`, `voice` (how we write, the placeholder convention), `offer`, `never` (what must never be shown or said). Skills read it before writing copy or judging images. |
| `site.pages` | How the kit reads the site. `html` (default): static pages by `glob`. `json`: one content file (`file`, `list`, `id`, `title`, `group`, `url` with `{id}`, `sections`, `heading`, `type`, `notes`, `ctas`). `command`: any build, printing the normalized list. |
| `site.current`, `site.root`, `site.toggles` | How the bar knows the page shown (`{"match": "path"}`, or `{"event", "path"}` for single-page sites that dispatch a render event), where open notes go, and draft toggles (a class on an element). |
| `theme` | `css`: the project's token and font stylesheets, loaded into the viewers. `map`: kit token → project value when names differ. |
| `data` | Where each tool keeps its data: `dir`, `history`, `gallery`, `atlas`, `scans`, `prompt_kit`, `concepts`. |
| `history` | `branch`, `checkpoints` `[{commit, title, note}]`, `skip` (path prefixes not part of the site), `copy` (prefixes that count as copy, not design). |
| `gallery`, `atlas` | `sources` for the generic gallery, or a `producer` command of the project's own (same output shape). |
| `notes` | Kit skill → a project notes file the skill reads first (project rules, naming, history). |
| `tools`, `skills`, `refresh`, `checks` | The project's own tools (shown in the bar and the hub), skills, generator steps and check commands, run by `refresh`. |
| `copies`, `release`, `live.keep` | Published copies (production, staging, dev, live preview, draft), which carry the studio, and the only files the live site is made of. |

## Detaching for the live site

The site never depends on the studio. In every site page the studio is one block:

```html
<!-- studio: development tooling (studio.config.json). ... -->
<link rel="stylesheet" href="studio/web/studio.css">
<script defer src="studio/web/studio.js" data-tool="site"></script>
<!-- /studio -->
```

`python studio/studio.py release <out>` copies only `live.keep`, cuts every studio block and fails on any studio file or broken link left. `check` runs it as a dry run. The Pages workflow (`assemble`) publishes `live/` (production released) beside the tooled copies, so the live site can be reviewed first. Going live is `"release": {"production": false}`: the root serves the released site and the tooled production moves to `draft/`.

## Commands

| Command | Does |
| --- | --- |
| `about [tool]` | Each tool: what, when, reads, writes, how to refresh, its skill |
| `status` | Tools whose sources changed after their outputs |
| `refresh [tool ...] [--history]` | Page index, WebP, gallery, atlas, the project's steps, the bar; then the project's checks and `check` |
| `check` | Config and tool rules, skills installed and current, generated files current, dry-run release |
| `build` | `web/studio.js`, `<data.dir>/studio.json`, `<data.dir>/pages.json`, the history service worker |
| `pages` | The page index only |
| `history` | Page history from the production branch (heavy; run on it) |
| `gallery` | Gallery manifest and thumbnails |
| `atlas` | Atlas index from the image descriptions |
| `prompts <out.json> [page ids]` | One image prompt per section from the prompt kit |
| `scan <url> [--max N]`, `scan compare <site> [<page>]`, `scan compare --all`, `scan import <site> <file.html> [<url>]`, `scan list` | Site scans |
| `motion search "<words>"`, `motion get <slug> --out <dir>`, `motion guide <topic>`, `motion catalog` | Subframe Motion library |
| `release <out> [--from <checkout>]` | The live site into a folder |
| `assemble <site> <branch>=<checkout> ...` | The Pages site from branch checkouts |
| `install`, `init [--name]`, `doctor` | Set up and update |

## For agents

- Read the project's `AGENTS.md` and this file, then `studio.config.json`. `python studio/studio.py about` maps the tools; each names its skill.
- Kit skills read the project through the config and the project's notes (`notes`); the notes win over the skill.
- Never edit generated files: `web/studio.js`, everything in `<data.dir>/`, a tool's `outputs`. Edit sources, then `refresh` or `build`.
- Keep the kit generic. A change only one project needs goes in its config, its notes or its own tool, never in `studio/`. A change every project would want goes in the kit, without naming a project, and `python studio/studio.py install` in each project picks it up.
- Several agents can work at once: tools have separate sources, and every generated file is rebuilt from them, so whoever commits runs `refresh` (or `build`) and `check` last.
- Report skipped `refresh` steps (no Pillow, a missing working folder) to the person you work for.
